下表中 **【已有】** 表示仓库具备相应 Python 代码或契约；**【其他人需实现/联调】** 表示真实前端、资产、仿真/相机或 Control 接口尚需部署接入。C、E、R 是业务阶段，不是固定函数调用次数。执行中的详细实例 ID 为团队 Scene v1 的非负整数；第一次 Qwen 使用的语义 `entity_id` 仍为字符串。`LocalScenePlatform` 的 ACK 仅代表本地元数据确认，**不等于仿真真正加载**。

## 表一：共用处理 C1–C5（编辑与机器人任务都经过）

| 阶段 | 实际函数调用链（按顺序） | 输入 → 本阶段处理 | 输出结构与下一步用途 | 其他人需实现/对接的接口（放在发生阶段） |
|---|---|---|---|---|
| **C1 接收任务** | `cli.main()` → `BrainApplication.handle(instruction, session_id, scene_path)` → `SessionStore.lock()` → `BrainApplication._handle()` | **输入**：原始用户文本、可选 `session_id`、可选上传场景文件路径。为本轮生成 `request_id`，初始化 `BrainRunReport`；同一 Session 锁防止并发覆盖。`BrainApplication.__init__()` 已在启动时完成配置和 Provider 初始化，不是每轮重建。 | **输出**：带 `session_id/request_id` 的本轮处理上下文；进入 C2。最终 `handle()` 返回 `BrainRunReport`（成功、阻塞/失败、回复、产物路径）。 | **【前端/总控入口】** 当前有 CLI/Python API，**没有已联调的前端 HTTP 服务**。前端或网关需把文本与 session ID 交给 `handle()`，并把 `BrainRunReport.reply/run_status/artifacts` 展示给用户；用户上传场景需落实为可读取的文件路径或新增应用层输入适配。 |
| **C2 恢复会话、导入旧场景** | `BrainApplication.get_session()` → `SessionStore.load()`/`SessionStore.restore()`；若 `scene_path` 存在：`_load_scene()` → `SceneFileCodec.load()` → `BrainSession.initialize_scene()` → `platform.load_scene()` → `_check_snapshot()`。 | 从 `session_state.json` 恢复最新 Scene、`DialogueState`、`holding_object`、`sync_state`、pending 命令和整数 ID 的已用历史。用户提供 Scene 文件时，按**组件 Scene v1** Schema 校验后加载；旧 flat 场景不会自动转换。会话恢复也可能触发 `platform.load_scene()`。 | **输出**：可供本轮使用的 `BrainSession`；其中 `scene` 为已确认 `SceneConfig` 或 `None`，并有历史对象编号、对话状态和执行状态。进入 C3。注意导入 Scene 的**结构合法**不代表资产资源一定可解析。 | **【仿真/场景平台】** `ScenePlatformPort.load_scene(scene: SceneConfig) -> SceneSnapshot`：解析 `Transform/MetadataRef/Semantic/RobotDriver/Camera/Light` 等组件，真正创建/恢复仿真世界，并在加载完成后回 `scene_id + scene_version + accepted/error`。`parent=0` 是合法父 ID。**【前端/仿真需联调】** 会话恢复时如何重连现存场景，不能因重载意外重置正在执行的机器人。当前默认 `LocalScenePlatform.load_scene` 仅确认元数据。 |
| **C3 第一次 Qwen：任务理解** | `BrainPipeline.understand_turn()` → `DialogueState.contextualize()` → `TaskUnderstandingRequest()` → `QwenHTTPProvider.understand_turn()` → `_call(stage="task_understanding")` → `TaskParseOutput.model_validate()` → `TaskParseOutput.to_brain_turn()`（机器人任务进一步 `to_task_intent()`）。 | **输入给 Qwen**：用户文本，必要时附 `[dialogue_ref=…]`、`[dialogue_ref_set=…]` 之类语义提示；**不是整份 Scene，也没有 RGB**。模型按 Schema 给出 `status/turn_kind`、实体、数量、方位、操作、关系。Python 转换成 `BrainTurn`；机器人 payload 为 `TaskIntent`，编辑 payload 为 `SceneEditPlan`。 | **输出**：`BrainTurn(status, turn_kind, task_intent / scene_edit / scene_query / session_control)`；其中 `turn_kind` 决定后续进入 E 或 R。此时**没有具体 object ID、抓取点或轨迹**。 | **【其他人需部署：Qwen 服务】** 提供 OpenAI-compatible `POST /v1/chat/completions`，模型名由实际 `/v1/models` 核定，支持期望的 JSON Schema/结构化输出。**【前端需对接】** `clarification_required`/`unsupported_task` 的提示与后续补充输入。Qwen HTTP 客户端代码已实现，不代表模型服务永远在线。 |
| **C4 Python 规范化 + 会话门禁** | `DialogueState.apply_exclusions()` → `TaskDomainPolicy.classify()` → 机器人任务 `normalize_motion_language()`；之后 `BrainSession.check_turn()`。 | 把“另一个”处理为 Python 的实例排除；核对直接场景编辑/机械臂动作的任务域；明确米数优先、禁止无依据距离；检查 `pause/close`、`execution_pending`、`sync_state=unknown`。混合不兼容请求不能悄悄只执行一半。 | **输出**：通过检查、可进入 C5/E/R 的 `BrainTurn`；或者阻塞/错误报告。若是 `scene_query` 和 `session_control`，分别转场景查询/会话控制分支，不经过 E/R 主体。 | **【前端/Control 状态】** 前端正确显示澄清和阻塞原因；Control 必须在真正结束请求后回传执行反馈，否则会话可能保持 `execution_pending`，后续请求被阻止。此阶段 **Brain 内部已有**任务域与门禁实现。 |
| **C5 准备可用 Scene（仅缺场景时新建）** | **已有场景**：直接复用；**无场景且是编辑/机器人任务**：`SceneBootstrapper.prepare()` → `AssetResolver.resolve()` / `AssetLibraryPort.resolve()/find_by_name()/find_by_category()` → 几何布局与关系检查 → `BootstrapResult`。 | 从语义实体、配置和只读资产库建立基础组件 Scene：**桌子对象 + 机器人对象 + 任务要求的物体**，提供 `MetadataRef/Transform/Semantic/RobotDriver`，分配稳定整数 ID，依据包围盒、工作区和间距设置初始位置，不提前完成机器人的目标操作。 | **输出**：`BootstrapResult(scene, entity_candidates, asset_bindings, assumptions)`。**首次编辑**：先 `initialize_scene(基础Scene)` 再 E1–E7；**首次机器人任务**：先用候选 Scene 进行 R1–R7，成功后才 `initialize_scene()`。没有场景的查询不会偷偷新建。 | **【资产库】** `AssetLibraryPort.resolve(metadata_ref) -> BrainAssetView`，`find_by_name()/find_by_category()`；需真实 `MetadataRef`、几何 bounds、桌子资源、机器人资源，以及 `default_robot_driver`（关节顺序和限制）。**【仿真平台】** 当 `initialize_scene()` 实际发生时调用 `load_scene()` 真正载入； |

## 表二：场景编辑 E1–E7（例：“把苹果右移10厘米”）

| 阶段 | 实际函数调用链（按顺序） | 输入 → 本阶段处理 | 输出结构与下一步用途 | 其他人需实现/对接的接口（放在发生阶段） |
|---|---|---|---|---|
| **E1 进入场景编辑器** | `BrainSession.process_turn()` → `BrainPipeline.process_turn()` 判断 `turn_kind=scene_edit` → `SceneEditor.edit_result(turn.scene_edit, scene, dialogue, bindings_override, seen_scene_object_ids, next_scene_object_id)`。 | **输入**：`SceneEditPlan`（`entities/relations/operations`）、已确认的 `SceneConfig`、多轮指代和 ID 分配历史。创建**预演用** `SceneManager` 与本轮实体绑定表，暂不改正式 Scene。 | **输出**：编辑上下文，准备对每条 `SceneEditIntent` 顺序求值；可以一轮多个编辑操作。 | **【已有】** 此处纯 Brain； |
| **E2 选择目标对象/参照物** | `SceneObjectSelector.resolve()` → 内部构造选择用 `TaskIntent` → `DialogueState.bindings()` → `SceneGrounder.ground()` → `SemanticEntitySelector.select()` → `discover_candidates()` → `SceneRelationResolver.resolve()`（位置关系使用 `world_transform()`）。 | **输入**：如 “苹果”“最左边的苹果”“篮子右边的苹果”、当前 Scene vN、上一轮绑定。按 `Semantic.semantic_name/category`、别名、数量、排除和空间关系查找；不靠 `object_name_in_scene` 猜语义。 | **输出**：具体 `SceneObject`/实例 ID，例如 `apple→object_id_in_scene=2`，参照物则单独绑定。用于 E3 计算哪一个对象需要编辑。 | **【场景数据生产方】** 上传/加载的对象应填可靠 `Semantic` 和 `Transform`，否则无法按自然语言匹配。**【尚未实现】** 编辑分支遇歧义**没有视觉 fallback**，不能要求 Camera/VLM 自动替它选目标；目前会阻塞/报歧义。 |
| **E3 按编辑类型构造变化** | **新增** `_add()` → `AssetResolver.resolve()` → `_placement()` → `make_object()`；**删除** `_modify(remove)`；**平移** `_modify()` → `world_transform()` → `translate()` → `local_from_world()`；**旋转** 同理使用 `rotate()`；**相对放置** 使用 `SceneLayoutPolicy.relative_transform()`。 | **输入**：目标对象、操作类型、方向、精确/模糊距离或相对参照物。新增读资产 `MetadataRef`/局部 AABB；编辑先在世界系计算，再转回父系局部 `Transform`（不可表达为TRS的剪切会拒绝）。此处是**直接场景修改**，不是 IK/轨迹规划。 | **输出**：`ScenePatchOperation` 列表：`add_object/remove_object/upsert_component/remove_component`；如更新对象2的 `Transform`。 | **【资产库】** 新增和需要几何的编辑能通过 `AssetLibraryPort` 解析 `MetadataRef` 并获取 bounds。**【当前限制】** 任意 `edit.properties` 修改尚不支持，不能声称可自然语言修改任意颜色、相机/灯光或 RobotDriver 字段。 |
| **E4 逐步预演、检查碰撞与 support** | 临时 `SceneManager.apply_patch()` → `SceneEditor._overlaps()` → `SpatialFactResolver.infer_support()` → 可能追加 `Semantic` 的 `upsert_component` → 继续在候选 Scene 应用。 | 对一轮中的每条编辑按顺序计算，使“新增苹果，再移动它”可使用刚增加的对象。检查 ID、父子引用、包围盒重叠/支撑；位姿改变需重新确认 `Semantic.support`。**包围盒几何检查不是物理仿真/机器人物理碰撞**。 | **输出**：经过校验的预演场景、可能附加 `support` 更新的补丁操作；待 E5 统一合并。若几何未知/支撑不能证明则可能明确拒绝；也存在缺少几何时跳过重叠检查的保守边界。 | **【资产/场景平台】** Geometry/AABB 与 `Transform.parent` 坐标约定一致。 |
| **E5 合并生成正式 ScenePatch** | `SceneEditor.edit_result()` 收集所有预演操作 → 再以 `SceneManager.apply_patch()` 校验整体 → 返回 `SceneEditResult` → `BrainPipeline.process_turn()` 返回 `BrainResult(scene_patch=...)`。 | 将多操作变成同一份 `ScenePatch(scene_id, base_scene_version, operations)`，检查最终组件场景结构有效，记录新增/删除/焦点对象。中间候选版本变更不代表正式每步都提交。 | **输出**：`SceneEditResult.patch` 和焦点/新增/删除 ID；每轮正式 patch 使 `scene_version` **只增加1**。转 E6。 | **【仿真端协议】** 必须接受当前组件 Patch 的四种 `action`，而不是旧 flat `update_transform`；`upsert_component` 替换完整组件。若仿真端只支持全量加载，可由**外部 Adapter**在 `apply_patch()` 内生成完整新 Scene 再加载。 |
| **E6 真正应用仿真并确认提交** | `BrainSession._accept_result()` → `BrainSession.apply_scene_patch()` → 候选 `SceneManager.apply_patch()` → **`platform.apply_patch(patch)`** → `BrainSession._check_snapshot()` → `_commit_manager()` → `DialogueState.observe()`。 | Brain先在内存中预演，再请求场景平台应用；平台返回 `SceneSnapshot(scene_id, scene_version, accepted, error)`；必须匹配预期新版本才能正式采用候选 Scene。失败/确认不一致时 `sync_state=unknown`。 | **输出**：**已确认的**新 `SceneConfig vN+1` + 更新后的对话焦点。下一轮编辑从 vN+1 继续，而不是从旧文件重建。 | **【仿真/场景平台】** `ScenePlatformPort.apply_patch(patch: ScenePatch) -> SceneSnapshot`，**真正**更新仿真实体/组件、保留未修改组件、处理父子关系与资源实例，再在应用完毕后 ACK 正确版本；不能仅收到请求就返回成功。**【前端需对接】** 仿真刷新/重新渲染并展示新场景。 |
| **E7 保存本轮和准备下一轮** | `BrainApplication._save_session()` → `SessionStore.save()`；`ArtifactWriter.publish()` → `BrainRunReport`。 | 把 `SceneConfig vN+1`、`DialogueState`、历史整数编号、状态写入会话 checkpoint；本轮产物先在 staging 生成再发布。保留前一请求目录。 | **输出文件**：`session_state.json`；本轮 `request_record.json/result.json/scene_config.json/scene_patch.json`。**没有**机器人 `commands.json`；对前端回复“场景元数据已更新（未运行仿真）”的文本来自现有 Brain 业务逻辑。 | **【前端/仿真持久化】** 通过 `result.artifacts.scene_config` 或新版本 Scene 显示结果；跨进程/断线恢复时调用 C2 的 `load_scene()` 重连真实场景。**不要把每轮 `app.load_scene()` 当作增量编辑同步**，它会重置对话、已导出命令等会话状态。 |

## 表三：机械臂任务 R1–R8（例：“把两个苹果放进篮子”）

| 阶段 | 实际函数调用链（按顺序） | 输入 → 本阶段处理 | 输出结构与下一步用途 | 其他人需实现/对接的接口（放在发生阶段） |
|---|---|---|---|---|
| **R1 进入机器人分支 + 合并稳定指代** | `BrainSession.process_turn()` → `BrainPipeline.process_turn()` → `DialogueState.bindings(intent, scene)`，与 `bindings_override` 合并并检查冲突。 | **输入**：`TaskIntent`（语义实体/操作/数量/目标关系）、当前 `SceneConfig`、DialogueState 和 `holding_object`；“它/它们”先使用会话里保存的整数实例 ID；首次建场景可带 bootstrap 已知绑定。 | **输出**：本轮实体的约束绑定表 `overrides: semantic_entity_id → list[object_id]`；交 R2，不需要模型再猜实例编号。 | **【执行状态回写】** Control 要通过后续 `ExecutionFeedback` 提供真实 `holding_object`，否则下一轮“把它放下”不能正确认定夹爪已持物。R1 本身由 Brain 实现。 |
| **R2 语义 Grounding（歧义时可拍照/VLM）** | 常规：`SceneGrounder.ground()` → `SemanticEntitySelector.select()` → `SceneRelationResolver.resolve()`。**条件支路**：抛出 `GroundingAmbiguous` → `BrainSession.capture()` → **`platform.capture(CameraRequest)`** → `VisionFallbackGrounder.resolve()` → `QwenHTTPProvider.detect(frame, [VisionEntity])` → `_iou()` → `overrides` → **重新** `SceneGrounder.ground()`。 | 将 `apple`、`basket` 对齐到当前 Scene 中 `Semantic` 实例。歧义且启用 vision 时从场景平台取**同一 scene_id/version**的 `CameraFrame`（PNG编码RGB与**已知ID的**归一化 `instance_boxes`）；发给 Qwen 的只是 RGB + `entity_id/semantic_name`，其输出仅 `detections[{entity,bbox}]`。Python按 IoU（默认≥0.5）把框对回实例，不能让 VLM凭空给 `object_id`。 | **输出**：`GroundedTask`（例如 `apple→[2,3]`，`basket→[4]`），含 `metadata_ref`、`model_scale`、场景 ID/版本。**注意**“绑定成功”不等于已找到机器人抓取位姿。 | **【相机/仿真】** `ScenePlatformPort.capture(request: CameraRequest) -> CameraFrame`，按 `camera_id`选择实际场景相机、拍照/渲染、输出 PNG RGB bytes 和与同帧对应的实例 `bbox+整数ID`，保持 `scene_id/scene_version` 同步；相机字符串 ID 与 Scene 整数相机实例的映射要约定。**【Qwen 服务】** 现有 `detect()` 可请求 VLM，正式图像功能需实际支持。**【当前限制】** 编辑分支无此支路；颜色缺证据/对象不存在不保证触发视觉；仅有 RGB、没有 instance_boxes 仍无法用当前算法消歧。 |
| **R3 集合/多操作实例展开** | `TaskExpander.expand(grounded, scene)`。 | 对 `apple→[2,3]` 建 `apple__01→2`、`apple__02→3`；将一个高层 `pick_and_place` 展开为对应多个具体 operation（例如 `op-1__01/op-1__02`），保留数量、配对关系、执行依赖。 | **输出**：**实例级** `GroundedTask`：每个实体 `scene_object_ids` 只有一个成员；R5/导出器不再面对“target是一个列表”。 | **【已有】** Brain 内部实现，无直接外部调用。 |
| **R4 解析模糊移动距离** | `MotionScaleResolver.resolve()` → **`AssetLibraryPort.resolve(entity.metadata_ref)`** → `MotionPolicy.scale_factor()`。 | 仅对需要数值解析的 `move`：从模型尺寸、当前实例 world scale、方向轴把 `small/medium/large` 换算成 `distance_m`（比例10%/50%/200%）；明确数值保持用户原值。 | **输出**：带确定性距离的实例级 `GroundedTask`，交技能规划 R5；不要求每个 pick-and-place 都额外算一段位移。 | **【资产库】** 对 `MetadataRef` 返回正确 `dimensions_m/local AABB` 和几何原点约定。真实机器人步长安全、碰撞和轨迹仍在 Control 检查，不由这一步保证。 |
| **R5 生成 Atomic SkillPlan** | `SkillPlannerRouter.plan()` → **recipe**：`RecipePlanner.supports()/plan()`；**qwen**：`build_planner_context()` → `REGISTRY.prompt_catalog()` → `QwenHTTPProvider.plan()` → `SkillPlanLLMOutput` → `enrich_skill_plan()`；**auto**：只依据 recipe 支持情况选择。 | **输入**：已绑定、已展开、距离规范化的 GroundedTask + 当前持物状态。输出 `locate/move/grasp/release/press/pull/push` 技能组合及 role/region；如一个苹果放置通常是定位源→接近→抓取→定位目标→移到 placement_region→释放。默认 `recipe` 不做第二次 Qwen。 | **输出**：`SkillPlan(steps: list[SkillStep])`，含 `step_id/operation_id/skill_name/target_entity/reference_entity/region`；交 R6。不是 Control 的关节轨迹。`search` 尚无可导出技能，明确拒绝。 | **【Qwen服务】** 配置 `planner=qwen` 时需额外一次 `skill_planning` 模型请求；非必需。 |
| **R6 技能计划门禁** | `PlanValidator.validate(task, plan, scene, held_object)`（Router 里执行；R7 导出器也会再执行）。 | 检查操作/步骤覆盖、顺序、依赖、角色合法性、scene版本、目标是否存在、位移不重复、已持物和抓取/释放/放置状态前提；禁止省略关键动作或多次位移。 | **输出**：通过验证的 `SkillPlan` 或明确错误；通过才可导出 R7。 | **【已有】** Brain 内部实现，无直接外部调用。 |
| **R7 转为 Commands v2** | `CommandExporter.export()` → 再次 `PlanValidator.validate()` → 语义实体绑定替换为整数实例 ID → `CommandsFile` / `canonical_commands()`。 | `SkillStep.target_entity="apple__01"` 转成 `Command.parameters.target=2`；放置参照如篮子转成 `CommandPlacementTarget.reference=4`。为每步生成 `command_id/source_skill_step_id/operation_id/skill_name/parameters`；顶层含 `request_id/scene_id/scene_version/robot/operations/commands`。 | **输出**：`CommandsFile`（后续保存 `commands.json`），包含语义 region 或 `motion_direction+distance_m` 的两种互斥 move 形式； | **【机器人实例路由】** 当前顶层 `robot` 来自 Brain 配置字符串，不自动解析 Scene 中某个 RobotDriver 对象；部署时要明确配置机器人与场景机器人实例的对应关系。 |
| **R8 计划发布 → 外部执行 → 反馈恢复** | **Brain已有**：`BrainSession._accept_result()` → `BrainApplication._save_session()` → `ArtifactWriter.publish()`。**外部投递应接入已有 API**：`BrainApplication.mark_dispatched(session_id, commands)`；执行完成调用 `BrainApplication.apply_execution_feedback(session_id, feedback, confirmed_scene=...)` → `BrainSession.apply_execution_feedback()` → `platform.load_scene(confirmed_scene)`。 | 成功规划先保存导出记录和本轮文件，`BrainRunReport.executed=false`。之后**由外部调度**把命令交 Control；`mark_dispatched()`只做会话 pending 登记，**不会自己调用机械臂**。Control执行后回 `ExecutionFeedback(request_id/status/commands/holding_object)`，并提供同 `scene_id`、更新 `scene_version` 的完整权威 `SceneConfig`，Brain 才能同步物体/持物并进入下一轮。 | **输出文件**：`commands.json`、`scene_config.json`、`result.json`、`request_record.json` 和 `session_state.json`。**执行反馈后**：`pending` 清除，持物/场景状态更新；无权威场景快照时 `sync_state=unknown`，不能把规划输出当执行成功。 | **【总控/Control/仿真闭环】** ① 可靠下发 Commands v2 或适配协议，并与 `mark_dispatched()` 做幂等/确认协调；② Control 真正执行并回传逐 command 结果；③ 仿真/场景平台形成**执行后完整场景快照**（机器人动作可能移动物体，不能使用执行前 Scene）；④ `platform.load_scene(confirmed_scene)` 确认同步。**【当前缺口】** Brain 没有现成的完整跨服务消息传输事务、Control执行器或真实场景重建服务；不能把函数入口当成已联调系统。 |

**最关键的三处跨团队接线位置**：C2/C5 的 `platform.load_scene()`（首次/恢复加载）；E6 的 `platform.apply_patch()`（多轮场景修改与确认）；R2 的 `platform.capture()`（照片和实例框）；R7–R8 的 Commands v2 交付、实际执行和 `apply_execution_feedback()`（执行后权威场景回写）。**这些必须以外部真实 ACK/反馈为准，不能用 `LocalScenePlatform` 的元数据 ACK 冒充仿真完成。**
